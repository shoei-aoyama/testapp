# 在庫管理システム DB設計書 v1.1

対象: 要件定義書 v2.1 / DB: MariaDB（XAMPP、開発DB名 `testapp`）

---

## 1. この設計で使う5つの仕組み

要件定義書のルールをDB側でも守るために、以下を使う。先に何か・なぜ・メリットとデメリットを説明する。

### 1.1 外部キー制約の `RESTRICT`

- **何か**: 「他のテーブルから参照されているレコードは削除できない」とDBが止める設定。
- **なぜ使うか**: 要件の削除条件（履歴がある商品は削除不可、移動で使われている倉庫は削除不可など）を、アプリのバグがあってもDBが最後に守るため。
- **メリット**: UseCaseの削除チェックに漏れがあっても、履歴付きのデータが消えない。
- **デメリット**: 削除時に、先に子のレコードを消す順序をUseCaseが守る必要がある（例: 商品削除時は、0在庫の `inventories` を先に削除してから `products` を削除する）。

### 1.2 CHECK制約

- **何か**: 「この列はこの条件を満たす値だけ入れられる」とDBに定義する仕組み（例: 数量は1以上）。MariaDB 10.2.1以降で有効。
- **なぜ使うか**: 数量0、不正な種別、不正なステータス、状態と日時の食い違いを、DBレベルで拒否するため。
- **メリット**: Validationやテストをすり抜けた不正データも保存できない。テストで「DBが拒否すること」まで確認できる。
- **デメリット**: 条件を変えるときはマイグレーションが必要。ステータス値などを増やす際に制約の修正を忘れるとエラーになる。

### 1.3 悲観ロック（`lockForUpdate`）

- **何か**: 在庫行を読む時点で「この行は私が使う」とDB上でロックし、他の処理を待たせる方式。
- **なぜ使うか**: 要件6.1「同時操作でも在庫が0未満にならず、整合性を保つ」を満たすため。
- **メリット**: 在庫のような「取り合いが起きる値」の整合性を、確実かつ単純に守れる。
- **デメリット**: 同じ在庫への操作が待たされる。ロックの取得順がバラバラだと、処理同士が互いに待ち続けるデッドロックが起きうる。
- **取得順のルール（UseCase設計で守る）**: 複数の `inventories` 行をロックするときは、必ず `product_id` 昇順、次に `warehouse_id` 昇順で取得する。

### 1.4 複合外部キー

- **何か**: 通常の外部キーは「1列が相手の1列と一致する」ことを守るが、複合外部キーは「2列の組が、相手の2列の組と一致する」ことを守る。ここでは `stock_movements` の（移動明細ID, 商品ID）の組が、`stock_transfer_items` の（ID, 商品ID）の組と一致していることを守る。
- **なぜ使うか**: 履歴を移動明細に紐づけても、履歴自身が `product_id` を持つため、「明細は商品A、履歴の商品は商品B」という食い違いが入れられてしまう。それをDBに拒否させるため。
- **メリット**: 履歴と移動明細の商品の食い違いが、アプリのバグがあってもDBレベルで起きない。
- **デメリット**: 参照先の `stock_transfer_items` に（ID, 商品ID）のユニーク制約を追加する必要があり、マイグレーションが少し複雑になる。履歴の商品と倉庫の整合（TRANSFER_OUTは移動元、TRANSFER_INは移動先）までは守れないため、倉庫の一致はUseCaseとテストで確認する。
- **補足**: 移動明細IDがNULLの履歴（入庫・出庫・棚卸調整）では、この制約はチェックされない。

### 1.5 在庫行の作成手順（作成を試みてから、ロックする）

- **何か**: `inventories` の行がなければ作成し（すでにあれば何もしない）、その後で `lockForUpdate` で行をロックする、という2段階の手順。Laravelでは `insertOrIgnore` で行を作り、続けてロック付きで取得する。
- **なぜ使うか**: 存在しない行はロックできないため。同じ商品×倉庫への初回入庫が同時に来ると、両方が「行がない」と判断して作成を試み、片方がユニーク制約エラーになる。先に作成を試みておけば、どちらの処理もその後は必ず行をロックでき、エラーにならない。
- **メリット**: 初回入庫の同時実行でも、エラーにならず整合性が守られる。0在庫の行を常に持たずに済む。
- **デメリット**: 毎回、作成を試みるクエリが1回増える。複数の行を扱うときも、作成とロックの順序を `product_id` 昇順、次に `warehouse_id` 昇順で統一しないと、1.3と同じデッドロックの恐れがある。
- **ユニーク制約との関係**: `UNIQUE(product_id, warehouse_id)` が、行が重複しないことの最後の安全網になる。

## 2. テーブル一覧

| テーブル             | 役割                                              |
| -------------------- | ------------------------------------------------- |
| users                | ユーザー（Laravel標準に role / is_active を追加） |
| categories           | カテゴリマスタ                                    |
| products             | 商品マスタ                                        |
| warehouses           | 倉庫マスタ                                        |
| inventories          | 現在庫（商品 × 倉庫）                             |
| stock_transfers      | 倉庫間移動（ヘッダ）                              |
| stock_transfer_items | 倉庫間移動の明細（商品と数量）                    |
| stock_movements      | 在庫変動履歴（唯一の履歴）                        |

関連:

```text
categories 1 ── n products
products   1 ── n inventories n ── 1 warehouses
stock_transfers 1 ── n stock_transfer_items n ── 1 products
stock_transfers n ── 1 warehouses（移動元） / n ── 1 warehouses（移動先）
stock_movements n ── 1 products / warehouses / users
stock_movements n ── 0..1 stock_transfer_items（倉庫間移動由来のみ）
```

| ----------------------- | ------------------ | ---- | ----------------------------------------------- |

| cancelled_at            | timestamp          | YES  |                                                 |

CHECK:

- 移動元 ≠ 移動先
- status が3値のいずれか
- status と実行者・日時の整合: pending は完了系・キャンセル系がすべてNULL、completed は完了者・完了日時のみあり、cancelled はキャンセル実行者・日時のみあり

### 3.7 stock_transfer_items

| 列                      | 型                      | NULL | 備考           |
| ----------------------- | ----------------------- | ---- | -------------- |
| id                      | bigint unsigned PK      | NO   |                |
| stock_transfer_id       | FK → stock_transfers.id | NO   | RESTRICT       |
| product_id              | FK → products.id        | NO   | RESTRICT       |
| quantity                | unsigned int            | NO   | 1以上（CHECK） |
| created_at / updated_at | timestamp               | YES  |                |

- UNIQUE(stock_transfer_id, product_id)
- UNIQUE(id, product_id)（stock_movements の複合外部キーの参照先にするため。1.4参照）

### 3.8 stock_movements

| 列                     | 型                 | NULL | 備考                                                                   |
| ---------------------- | ------------------ | ---- | ---------------------------------------------------------------------- |
| id                     | bigint unsigned PK | NO   |                                                                        |
| product_id             | FK → products.id   | NO   | RESTRICT                                                               |
| warehouse_id           | FK → warehouses.id | NO   | RESTRICT                                                               |
| type                   | varchar(20)        | NO   | IN / OUT / ADJUSTMENT_IN / ADJUSTMENT_OUT / TRANSFER_IN / TRANSFER_OUT |
| quantity               | unsigned int       | NO   | 1以上（CHECK）。正数のみ                                               |
| quantity_before        | unsigned int       | NO   | 変更前在庫数                                                           |
| quantity_after         | unsigned int       | NO   | 変更後在庫数                                                           |
| reason                 | varchar(50)        | YES  | 理由は固定しないため文字列（NULL可）                                   |
| user_id                | FK → users.id      | NO   | 実行者。RESTRICT                                                       |
| stock_transfer_item_id | bigint unsigned    | YES  | 倉庫間移動由来のみ。複合外部キー（下記）                               |
| created_at             | timestamp          | NO   | 実行日時。初期値 現在時刻                                              |

- `updated_at` は持たない（履歴は追記のみで、更新しない）。Model側で `UPDATED_AT = null` を指定する。
- 複合外部キー: (stock_transfer_item_id, product_id) → stock_transfer_items (id, product_id)、RESTRICT
- UNIQUE(stock_transfer_item_id, type)（1つの明細につき TRANSFER_OUT / TRANSFER_IN は各1件まで。NULLは重複可）
- インデックス: created_at / (product_id, created_at) / (warehouse_id, created_at) / type

CHECK:

- 種別が6値のいずれか
- 増加系（IN, ADJUSTMENT_IN, TRANSFER_IN）は `quantity_after = quantity_before + quantity`
- 減少系（OUT, ADJUSTMENT_OUT, TRANSFER_OUT）は `quantity_after + quantity = quantity_before`
- TRANSFER系のときだけ `stock_transfer_item_id` が必須、それ以外はNULL

関連する移動（`stock_transfers`）は、移動明細を経由してたどる。

## 4. DBで守るものと、UseCaseで守るもの

| ルール                                                                                | 守る場所                                             |
| ------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 数量1以上、種別・ステータスの値、移動元≠移動先、変更前後の数量の整合                  | DB（CHECK）                                          |
| 商品コード・カテゴリ名・倉庫コードの重複、同一移動内の同一商品、商品×倉庫の在庫の重複 | DB（UNIQUE）                                         |
| 1つの移動明細に対する TRANSFER_OUT / TRANSFER_IN の重複作成不可                       | DB（UNIQUE）                                         |
| 履歴の商品と、紐づく移動明細の商品の一致                                              | DB（複合外部キー）                                   |
| TRANSFER_OUTの倉庫が移動元、TRANSFER_INの倉庫が移動先であること                       | UseCase＋テスト                                      |
| 在庫行がない場合の作成（作成を試みてからロック）                                      | UseCase（1.5）                                       |
| 履歴・移動・参照のあるマスタの削除不可                                                | DB（RESTRICT）＋UseCase                              |
| 在庫が0未満にならない                                                                 | DB（unsigned）＋UseCase（事前チェック）              |
| 同時操作での整合性                                                                    | UseCase（悲観ロック、取得順は1.3）                   |
| 無効な商品・倉庫・カテゴリの使用不可                                                  | UseCase                                              |
| 状態遷移（pendingからのみ変更可）、無効化後は完了不可・キャンセル可                   | UseCase                                              |
| 最後の有効なadminの無効化・降格不可、自分自身の無効化・権限変更不可                   | UseCase（複数adminの同時操作に備えて排他制御も行う） |
| 権限制御                                                                              | Policy / UseCase                                     |
| 削除時の0在庫行の同時削除                                                             | UseCase（同一トランザクション）                      |

## 5. 確認が必要な前提

- 単価は円単位の整数（`unsigned int`）とした。小数や外貨が必要なら `decimal` に変更する。
- 郵便番号・電話番号はハイフン付きの文字列で保存する前提で、桁数に余裕を持たせた。
- 申請日時は `created_at` を使い、`requested_at` は持たない。
