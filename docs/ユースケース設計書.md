# 在庫管理システム UseCase設計書 v1.0

対象: 要件定義書 v2.1 / DB設計書 v1.1

---

## 1. 方針

### 1.1 各層の役割

| 層            | 担当                                                                                              | 担当しないこと                           |
| ------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| FormRequest   | 入力の形式チェック（必須・整数・1以上・同一商品の重複・存在）と、画面向けのエラーメッセージ       | 在庫や状態に関わる判定                   |
| Gate / Policy | 誰が実行できるか（staff / manager / admin）                                                       | 状態に依存する判定                       |
| UseCase       | 処理手順、トランザクション、ロック、業務ルール（有効・無効、在庫不足、状態遷移、最後のadminなど） | HTTPの扱い、SQLの詳細、権限の判定        |
| Repository    | データの取得・登録・更新、ロック付き取得。呼ばれた通りにDB操作する                                | トランザクションの開始、業務ルールの判定 |

### 1.2 この設計で使う仕組み

要件定義書26章の構成（Controller → UseCase → Repository → Model）に、次の4つを加える。

| 仕組み                       | 何か                                                                                                                                              | なぜ使うか                                                                                                      | メリット                                                                           | デメリット                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 業務例外                     | 在庫不足・無効なリソース・不正な状態遷移など、業務ルール違反を表す専用のエラー。共通の親クラス `BusinessException` の子クラスにする               | UseCaseが失敗理由をはっきり伝え、Controller側が「業務エラーなら画面にメッセージを出す」と一括で処理できるように | テストで「この条件でこの例外」と検証できる。システムエラーと業務エラーを区別できる | クラスが増える。種類を増やしすぎると管理が面倒                                                 |
| Repositoryのインターフェース | Repositoryが持つメソッドの一覧だけを書いた契約。UseCaseは実際のクラスではなく、この契約に頼る（DI）。実装の割り当てはサービスプロバイダで登録する | 要件の「Repositoryをモック可能な構成」を素直に満たすため                                                        | UseCaseがDBの実装に依存しない。テストで偽物に差し替えやすい                        | Repositoryごとにインターフェースと実装の2ファイルになり、登録も必要                            |
| Gate                         | 「この操作は誰ができるか」に名前をつけて、1か所に登録する仕組み。Controllerやルートの `can:` から名前で判定できる                                 | 特定のModelに紐づかない権限（在庫操作など）をまとめるため                                                       | 権限のルールが1か所に集まる。ロール別の権限テストが書きやすい                      | 判定がUseCaseの外にあるので、UseCaseだけを呼ぶと権限チェックが働かない                         |
| デッドロックの自動再試行     | `DB::transaction` の第2引数に回数を指定すると、デッドロックで失敗したときにLaravelが処理をやり直す                                                | ロック順序を統一しても、予期しない組み合わせで起きる可能性がゼロではないため                                    | 利用者にエラーを見せずに済む                                                       | トランザクション内の処理が複数回実行されるので、外部への通知など副作用のある処理は入れられない |

### 1.3 Service

要件定義書26章のとおり、Serviceは必須の層としない。複数のUseCaseで共有される処理が出たものだけを作る。現時点では次の1つだけ。

- `StockItemGuard`: 入庫・出庫・棚卸・移動申請に共通する、明細の入力チェック（空でない、数量、同一商品の重複）。

## 2. 共通ルール

| ルール           | 内容                                                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| トランザクション | UseCaseが開始・終了する。`DB::transaction(..., 3)` とし、デッドロック時は最大3回まで再試行する。Repositoryは開始しない                                         |
| ロックの順序     | ① `stock_transfers` の1行 → ② `inventories` を `product_id` 昇順、次に `warehouse_id` 昇順。ユーザー管理では、有効なadminの行を `id` 昇順                      |
| ロックしたあと   | ロック取得後に読み直した値で判定・計算する。ロック前に読んだ値は使わない。更新は、ロック済みの行に対して行う                                                   |
| 在庫行の作成     | 在庫が増える可能性のある処理（入庫・棚卸・移動の完了先）は、行がなければ作成を試みてからロックする（DB設計書1.5）。出庫は作成せず、行がなければ在庫0として扱う |
| 実行者           | `execute()` の引数で `User` を受け取る。UseCaseの中で `auth()` は呼ばない                                                                                      |
| 入力の再チェック | FormRequestに加えて、UseCaseでも数量・同一商品の重複を確認する（HTTP以外から呼ばれても守るため。入庫・出庫には重複を防ぐDB制約がない）                         |
| 無効化との競合   | 商品・倉庫の有効チェックではロックしない。無効化の直前に実行された入庫などは許容する                                                                           |
| 対象外           | 入庫・出庫の二重送信（同じ操作の重複実行）の防止は、今回は対象外とする。状態遷移系（完了・キャンセル）の二重実行は、移動のロックと状態チェックで防ぐ           |
| 副作用           | トランザクション内では、メール送信などの外部への副作用を持つ処理は行わない（再試行されるため）                                                                 |

## 3. 業務例外

配置: `app/Exceptions/Business/`。すべて `BusinessException`（抽象クラス）を継承する。

| 例外                              | いつ投げるか                                                                                                                            | 持たせる情報                                                               | HTTP |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ---- |
| `InsufficientStockException`      | 出庫・移動完了で在庫が足りない                                                                                                          | 不足した商品ごとの（商品ID、倉庫ID、要求数量、現在庫）。複数あればまとめて | 422  |
| `InactiveResourceException`       | 無効な商品・倉庫・カテゴリを使おうとした                                                                                                | 種類（商品 / 倉庫 / カテゴリ）とID                                         | 422  |
| `InvalidStateTransitionException` | 倉庫間移動が pending でないのに完了・キャンセルしようとした                                                                             | 現在の状態、実行しようとした状態                                           | 409  |
| `ResourceInUseException`          | 削除条件を満たさない（履歴・在庫・移動・参照がある）                                                                                    | 種類とID、理由                                                             | 422  |
| `BusinessRuleViolationException`  | 上記以外の業務ルール違反（明細が空、数量が不正、同一商品の重複、移動元＝移動先、最後のadminの無効化・降格、自分自身の無効化・権限変更） | 理由を表すコード（例: `duplicate_product`, `last_admin`）                  | 422  |

- 存在しないIDは、Laravel標準の `ModelNotFoundException`（404）を使う。
- Controllerの手前で、`BusinessException` を一括で処理する（画面ではエラーメッセージ付きで元の画面に戻し、JSONではステータスコードとエラー内容を返す）。実装は `bootstrap/app.php` の例外処理で行う。

## 4. 権限（Gate）

`AppServiceProvider` の `boot()` で定義する。ルートでは `can:` で、Controllerでは `authorize` で判定する。

| Gate名          | 許可するロール | 対象の操作                                         |
| --------------- | -------------- | -------------------------------------------------- |
| `operate-stock` | manager, admin | 入庫、出庫、棚卸調整、倉庫間移動の完了、キャンセル |
| `manage-master` | admin          | 商品・カテゴリ・倉庫の管理                         |
| `manage-users`  | admin          | ユーザーの管理                                     |

ログイン済みのユーザー全員（staffを含む）ができる操作（各種閲覧、倉庫間移動の申請）は、ログインの確認だけを行い、Gateは作らない。

## 5. Repository

配置: インターフェースは `app/Repositories/Contracts/`、実装は `app/Repositories/Eloquent/`。割り当ては `RepositoryServiceProvider` で登録する（`bootstrap/providers.php` に追加）。

### 5.1 ルール

- Repositoryはトランザクションを開始しない。トランザクション内かどうかも確認しない。
- **`...ForUpdate` で終わるメソッドは、トランザクション内でのみ使う。** トランザクション外ではロックがすぐ解放され、意味がなくなる。インターフェースのコメントにも明記する。
- 単純な検索（読み取りのみ）は、Controllerから直接呼んでよい（8章）。

### 5.2 在庫操作に関わるインターフェース

| インターフェース                   | メソッド（案）                                                                                | 内容                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `InventoryRepositoryInterface`     | `insertMissing(array $pairs): void`                                                           | （商品ID, 倉庫ID）の組のうち、存在しない行を作成する。すでにあれば何もしない                           |
|                                    | `lockForUpdate(array $pairs): Collection`                                                     | 組を `product_id`・`warehouse_id` 昇順に並べて、存在する行をロックして返す（存在しない組は含まれない） |
|                                    | `updateQuantity(Inventory $inventory, int $quantity): void`                                   | ロック済みの行の数量を更新する                                                                         |
|                                    | `deleteZeroByProduct(int $productId): void` / `deleteZeroByWarehouse(int $warehouseId): void` | 在庫0の行を削除する（商品・倉庫の物理削除時）                                                          |
|                                    | `existsNonZeroByProduct(int $productId): bool` など                                           | 削除条件の確認                                                                                         |
| `StockMovementRepositoryInterface` | `create(array $attributes): StockMovement`                                                    | 履歴を1件作成する                                                                                      |
|                                    | `existsByProduct(int)` / `existsByWarehouse(int)`                                             | 削除条件の確認                                                                                         |
| `StockTransferRepositoryInterface` | `create(array $header, array $items): StockTransfer`                                          | ヘッダと明細を作成する                                                                                 |
|                                    | `findForUpdate(int $id): ?StockTransfer`                                                      | ヘッダをロックして取得する                                                                             |
|                                    | `markCompleted(StockTransfer $transfer, int $userId, CarbonInterface $at): void`              | completed にして完了者・日時を記録する                                                                 |
|                                    | `markCancelled(StockTransfer $transfer, int $userId, CarbonInterface $at): void`              | cancelled にしてキャンセル実行者・日時を記録する                                                       |
|                                    | `existsByProduct(int)` / `existsByWarehouse(int)`                                             | 削除条件の確認                                                                                         |
| `ProductRepositoryInterface`       | `findManyByIds(array $ids): Collection`                                                       | 複数の商品を取得する                                                                                   |
| `WarehouseRepositoryInterface`     | `find(int $id): ?Warehouse` / `findManyByIds(array $ids): Collection`                         | 倉庫を取得する                                                                                         |
| `UserRepositoryInterface`          | `lockActiveAdminsForUpdate(): Collection`                                                     | 有効なadminの行を `id` 昇順にロックして取得する                                                        |

マスタ・ユーザー管理の登録・更新・削除メソッドと、検索系のメソッドは、実装するときに確定する。

## 6. UseCase仕様（在庫操作・倉庫間移動）

配置: `app/UseCases/Stock/`、`app/UseCases/Transfer/`。1クラス1処理で、メソッドは `execute()` のみ。

明細の形式: `list<array{product_id: int, quantity: int}>`

### 6.1 StockInUseCase（入庫）

`execute(User $executor, int $warehouseId, array $items, ?string $reason = null): Collection`（作成した履歴を返す）

1. 明細を確認する（`StockItemGuard`。空でない、数量は1以上の整数、同一商品の重複なし）→ 違反は `BusinessRuleViolationException`
2. トランザクションを開始する（再試行3回）
3. 倉庫を取得する（なければ 404、無効なら `InactiveResourceException`）
4. 商品をまとめて取得する（1件でもなければ 404、無効な商品があれば `InactiveResourceException`）
5. `insertMissing` → `lockForUpdate`（昇順）
6. 商品ごとに、変更前の数量を記録し、在庫を増やし（`updateQuantity`）、IN の履歴を作成する
7. コミット

### 6.2 StockOutUseCase（出庫）

`execute(User $executor, int $warehouseId, array $items, ?string $reason = null): Collection`

1〜4. 入庫と同じ 5. `lockForUpdate`（昇順。作成はしない。存在しない行は在庫0として扱う）6. **全商品の在庫を先に確認する。** 1件でも不足していれば、不足した商品をすべてまとめて `InsufficientStockException` で報告する（何も更新しない）7. 商品ごとに、在庫を減らし、OUT の履歴を作成する 8. コミット

### 6.3 StocktakeUseCase（棚卸調整）

`execute(User $executor, int $warehouseId, array $items): Collection`（明細は `product_id` と `actual_quantity`（0以上の整数））

1. 明細を確認する（数量は0以上の整数、同一商品の重複なし）
   2〜4. 入庫と同じ
2. 実在庫が0より大きい商品の組だけ `insertMissing` → `lockForUpdate`（昇順。実在庫0の商品は、行がなければ作成しない）
3. 商品ごとに、現在庫（行がなければ0）との差分を計算する
    - 差分が0: 何もしない（履歴も作らない）
    - 実在庫が多い: ADJUSTMENT_IN（差分の数量）
    - 実在庫が少ない: ADJUSTMENT_OUT（差分の数量）
4. 差分のあった商品だけ、在庫を更新して履歴を作成する（理由はなし）
5. コミット（変更がなくても成功とし、空のCollectionを返す）

### 6.4 RequestTransferUseCase（移動の申請）

`execute(User $requester, int $fromWarehouseId, int $toWarehouseId, array $items): StockTransfer`

1. 明細を確認する。移動元＝移動先なら `BusinessRuleViolationException`
2. トランザクションを開始する
3. 移動元・移動先の倉庫を取得する（なければ 404、無効なら `InactiveResourceException`）
4. 商品を取得する（なければ 404、無効なら `InactiveResourceException`）
5. `create`（ヘッダは pending、申請者を記録。明細も同時に作成）
6. コミット。**在庫はロックも変更もしない**

### 6.5 CompleteTransferUseCase（移動の完了）

`execute(User $executor, int $transferId): StockTransfer`

1. トランザクションを開始する（再試行3回）
2. `findForUpdate`（なければ 404）
3. 状態が pending でなければ `InvalidStateTransitionException`（二重実行もここで止まる）
4. 明細・商品・移動元・移動先の倉庫を取得し、**1つでも無効なら** `InactiveResourceException`
5. 在庫の組を作る: 各明細の（商品, 移動元）と（商品, 移動先）。移動先の組だけ `insertMissing` する
6. すべての組を `lockForUpdate`（`product_id` 昇順、次に `warehouse_id` 昇順）
7. **全明細で移動元の在庫が足りるか確認する。** 1つでも不足なら、まとめて `InsufficientStockException`
8. 明細ごとに、移動元の在庫を減らして TRANSFER_OUT、移動先の在庫を増やして TRANSFER_IN の履歴を作成する（履歴には明細IDを紐づける。倉庫は、OUT が移動元、IN が移動先）
9. `markCompleted`
10. コミット

### 6.6 CancelTransferUseCase（移動のキャンセル）

`execute(User $executor, int $transferId): StockTransfer`

1. トランザクションを開始する
2. `findForUpdate`（なければ 404）
3. 状態が pending でなければ `InvalidStateTransitionException`
4. `markCancelled`（商品・倉庫が無効でもキャンセルできる。在庫は動かさない）
5. コミット

## 7. マスタ・ユーザー管理のUseCaseのルール

実装の順序は最後のため、ここではルールだけを定める。メソッド（案）は、実装するときに確定する。

| 対象     | 操作                       | 主な業務ルール                                                                                                                                                                                                    |
| -------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 商品     | 作成・更新                 | 新しいカテゴリに変えるときは、有効なカテゴリのみ（変更しないなら、無効カテゴリのままでもよい）                                                                                                                    |
|          | 無効化・有効化             | pendingの移動があっても無効化できる（完了はできなくなる）                                                                                                                                                         |
|          | 物理削除                   | 履歴・移動での使用がなく、現在庫がない（またはすべて0）場合のみ。条件を満たさなければ `ResourceInUseException`。在庫行をロックして条件を確認し、0在庫の行を先に削除してから商品を削除する（同一トランザクション） |
| カテゴリ | 作成・更新・無効化・有効化 | —                                                                                                                                                                                                                 |
|          | 物理削除                   | 1商品からでも参照されていれば `ResourceInUseException`                                                                                                                                                            |
| 倉庫     | 作成・更新・無効化・有効化 | —                                                                                                                                                                                                                 |
|          | 物理削除                   | 商品の物理削除と同じ条件（履歴・移動での使用なし、在庫なし/すべて0）                                                                                                                                              |
| ユーザー | 作成・更新                 | adminのみ。パスワードはハッシュ化して保存                                                                                                                                                                         |
|          | 無効化                     | 自分自身は不可。最後の有効なadminは不可                                                                                                                                                                           |
|          | 権限変更                   | 自分自身は不可。adminから降格するとき、最後の有効なadminなら不可                                                                                                                                                  |

ユーザーの無効化・権限変更では、トランザクション内で `lockActiveAdminsForUpdate` を呼び、有効なadminの人数を確認してから更新する（複数のadminが同時に互いを無効化・降格しても、0人にならないようにする）。

## 8. 検索の扱い

- 読み取りだけの単純な検索（商品在庫検索、倉庫別在庫検索、履歴一覧、移動の一覧・詳細、ダッシュボードの直近100件）は、**ControllerからRepositoryのインターフェースを直接呼ぶ。** 中身のないUseCaseは作らない。
- 次のような処理が出たときに、UseCaseまたは読み取り専用のQueryクラスを作る。
    - 複数のRepositoryから集約する
    - 閲覧条件を組み立てる
    - 結果を加工する
    - 業務上の表示ルールがある
- どちらにするかは、実装するときに決める。

## 9. テスト方針

| 種類               | 実DB                                                               | 見るもの                                                                                                                       |
| ------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| UseCaseのUnit Test | 使わない（`DB::transaction` は実際のテスト用DB接続でそのまま動く） | **業務判断。** Repositoryは偽物に差し替え、例外の種類、判定の順序（ロック→確認→更新）、Repositoryに渡す値を確認する            |
| Repository Test    | 使う                                                               | クエリの結果、ロック付き取得の並び順、`insertMissing` が重複しないこと、制約（UNIQUE・CHECK・RESTRICT）、削除条件の判定        |
| Feature Test       | 使う                                                               | 画面・APIからの一連の流れ。**トランザクション、ロールバック、整合性（履歴と在庫）、権限、状態遷移、二重実行（完了を2回実行）** |

- `DB` ファサードのモックは使わない。UseCaseの業務ロジックでない部分（Laravelの呼び方）を、テストしないようにするため。
- UseCaseを完全にDBなしでUnit Testしたい場合は、トランザクションを実行する小さなインターフェースを作って差し替える方法がある。抽象化が1つ増えるため、必要になった時点で検討する。
- 同時実行（2つの接続でのロック待ち、デッドロック）の再現テストは、基本のテストが揃ってから検討する。

## 10. ファイル構成と実装順

```text
app/
  UseCases/
    Stock/        StockInUseCase, StockOutUseCase, StocktakeUseCase
    Transfer/     RequestTransferUseCase, CompleteTransferUseCase, CancelTransferUseCase
    Product/ Category/ Warehouse/ User/   （マスタ・ユーザー管理。後で確定）
  Services/       StockItemGuard
  Repositories/
    Contracts/    InventoryRepositoryInterface ほか
    Eloquent/     InventoryRepository ほか
  Exceptions/Business/   BusinessException ほか5種
  Providers/      RepositoryServiceProvider
```

実装順: 業務例外 → Repository（在庫・履歴・移動・商品・倉庫・ユーザー）→ `StockItemGuard` → 入庫 → 出庫 → 棚卸 → 移動の申請・完了・キャンセル → マスタ・ユーザー管理 → 検索。
