# 在庫管理システム 要件定義書 v2.2

## 1. システム概要

複数倉庫の商品在庫を一元管理する在庫管理システムを構築する。

商品ごと・倉庫ごとの現在庫を管理し、以下の在庫操作を行えるものとする。

- 入庫
- 出庫
- 棚卸調整
- 倉庫間移動

すべての在庫変動は履歴として保持し、現在庫と在庫変動履歴の整合性を維持する。

本システムはLaravelを使用し、Controller / UseCase / Repositoryによる責務分離を行う。

また、Feature Test、Unit Test、Repository Test、認可、状態遷移、トランザクション、Rollback等を含むテストを十分に実施できる構成とする。

---

# 2. ユーザー・権限

ユーザーには以下の3種類の権限を設定する。

## 2.1 staff

一般利用者。

可能な操作：

- ダッシュボード閲覧
- 商品在庫検索
- 倉庫別在庫検索
- 在庫変動履歴一覧の閲覧
- 倉庫間移動申請

以下の操作は不可とする。

- 入庫
- 出庫
- 棚卸調整
- 倉庫間移動の完了
- 倉庫間移動のキャンセル
- 各種マスタ管理
- ユーザー管理

## 2.2 manager

在庫管理担当者。

staffの操作に加えて以下を実行できる。

- 入庫
- 出庫
- 棚卸調整
- 倉庫間移動の完了
- 倉庫間移動のキャンセル

入庫・出庫・棚卸調整については申請制とせず、managerが即時実行できる。

## 2.3 admin

システム管理者。

すべての機能を利用できる。

加えて以下を管理する。

- 商品
- カテゴリ
- 倉庫
- ユーザー

ユーザーの新規登録は一般公開せず、adminのみがユーザーを作成できる。

---

# 3. 商品管理

商品は以下の情報を持つ。

- 商品コード
- 商品名
- カテゴリ
- 単価
- 有効 / 無効

商品コードは重複不可とする。

商品名は必須とする。

カテゴリは必須とする。

単価はNULLを許可する。

商品は原則として物理削除せず、無効化して管理する。

## 3.1 無効商品の扱い

無効商品は、以下の操作に使用できない。

- 入庫
- 出庫
- 棚卸調整
- 倉庫間移動の新規申請

無効商品でも、在庫の閲覧、在庫変動履歴の閲覧は可能とする。

## 3.2 商品の物理削除

adminについては以下の条件をすべて満たす商品を物理削除できる。

- 在庫履歴が存在しない
- 現在庫が存在しない、またはすべて0
- 倉庫間移動で使用されていない

削除条件を満たし、削除を実行した場合、その商品の現在庫が0の `inventories` レコードも同時に削除する。

履歴を持つ商品は削除不可とし、無効化のみ可能とする。

---

# 4. カテゴリ管理

商品は必ず1つのカテゴリに所属する。

カテゴリはマスタとして管理する。

初期データとして3件程度のカテゴリをSeederで登録する。

初期カテゴリ例：

- 商品
- 資材
- 備品

カテゴリは以下の情報を持つ。

- カテゴリ名
- 有効 / 無効

adminはカテゴリを追加・編集・無効化できる。

無効カテゴリは新しい商品のカテゴリとして使用できない。

カテゴリの物理削除は、1商品からでも参照されている場合は不可とする。どの商品からも参照されていないカテゴリのみ、adminが削除できる。

---

# 5. 倉庫管理

複数倉庫を管理する。

倉庫は以下の情報を持つ。

- 倉庫コード
- 倉庫名
- 郵便番号
- 住所
- 電話番号
- 有効 / 無効

郵便番号、住所、電話番号はNULLを許可する。

倉庫は原則として削除せず、無効化する。

## 5.1 無効倉庫の扱い

無効倉庫は、以下の操作に使用できない。

- 入庫
- 出庫
- 棚卸調整
- 倉庫間移動の新規申請（移動元・移動先のどちらにも指定不可）

無効倉庫でも、在庫の閲覧、在庫変動履歴の閲覧は可能とする。

## 5.2 倉庫の物理削除

adminのみ、以下の条件をすべて満たす倉庫を物理削除できる。

- 現在庫が存在しない、またはすべて0
- 在庫履歴が存在しない
- 倉庫間移動で使用されていない

削除条件を満たし、削除を実行した場合、その倉庫の現在庫が0の `inventories` レコードも同時に削除する。

---

# 6. 在庫管理

在庫は「商品 × 倉庫」の組み合わせ単位で管理する。

例：

福岡倉庫  
商品A：30個

東京倉庫  
商品A：5個

この場合、商品Aの総在庫は35個となる。

現在庫は `inventories` で管理する。

在庫数は0未満にしてはならない。

`inventories` のレコードは、商品 × 倉庫の組み合わせごとに必ず存在するとは限らない。レコードが存在しない場合は、在庫0として扱う。

レコードは、入庫または倉庫間移動の完了によって初めて在庫が増える時点で作成する。在庫が0になってもレコードは残してよい。

## 6.1 同時実行時の整合性

複数ユーザーが同一在庫を同時に操作した場合でも、在庫数および在庫履歴の整合性を保証し、在庫数が0未満にならないものとする。

具体的な排他制御の方式は、DB設計・UseCase設計で決定する。

---

# 7. 在庫変動履歴

すべての在庫変動は `stock_movements` に記録する。

在庫履歴は在庫変動に関する唯一の履歴として扱う。

入庫や出庫を表す別の操作履歴テーブルは作成しない。

履歴には最低限以下を保持する。

- 商品
- 倉庫
- 種別
- 数量
- 変更前在庫数
- 変更後在庫数
- 理由
- 実行者
- 関連する倉庫間移動明細（倉庫間移動による変動の場合のみ）
- 実行日時

数量は必ず1以上の正の整数として保存する。

数量の正負によって在庫変動を表現せず、種別によって増減方向を判断する。

例：

`OUT / quantity = 3`

とし、`quantity = -3` とはしない。

主な種別として以下を想定する。

- IN
- OUT
- ADJUSTMENT_IN
- ADJUSTMENT_OUT
- TRANSFER_IN
- TRANSFER_OUT

---

# 8. 共通入力ルール

入庫・出庫・棚卸調整・倉庫間移動申請に共通して、以下のルールを適用する。

## 8.1 数量

- 入庫・出庫・倉庫間移動の数量は、1以上の整数とする。
- 棚卸調整で入力する実在庫数は、0以上の整数とする。
- 0、負数、小数、数値以外はValidation Errorとする。

## 8.2 同一商品の重複指定

1回の処理内で、同一商品を複数行指定することはできない。

例：

商品A 6個  
商品A 6個

のような指定は、現在庫の多少にかかわらずValidation Errorとする。

この制約は、入庫・出庫・棚卸調整・倉庫間移動申請のすべてに適用する。

---

# 9. 入庫

managerおよびadminが実行できる。

複数商品を一括して入庫できる。

入庫した数量分、対象倉庫の現在庫を増加させる。

商品ごとに `stock_movements` を作成する。

対象の商品・倉庫は有効である必要がある。

対象の `inventories` レコードが存在しない場合は、入庫時に作成する。

一括処理の途中で1件でも失敗した場合は、すべての変更をRollbackする。

---

# 10. 出庫

managerおよびadminが実行できる。

複数商品を一括して出庫できる。

対象の商品・倉庫は有効である必要がある。

要求数量を満たせない商品が1件でも存在する場合、出庫処理全体を失敗とする。

部分出庫は行わない。

例：

現在庫：10  
出庫要求：15

結果：

- 出庫不可
- 現在庫は10のまま
- 在庫履歴も作成しない

複数商品を一括出庫する場合も、1商品でも在庫不足であれば全件Rollbackする。

---

# 11. 入出庫理由

入庫・出庫時に理由を設定できる。

理由は必須とせず、NULLを許可する。

画面上では5種類程度の理由をラジオボタンで用意する。

初期状態では未選択とする。

具体的な理由については業務用途によって変化するため、本システムのコア仕様として固定しない。

---

# 12. 棚卸調整

managerおよびadminが実行できる。

対象の商品・倉庫は有効である必要がある。

棚卸時には増減数量を直接入力せず、「実際に確認した在庫数」を入力する。

例：

システム上の在庫：10  
実在庫：8

システムが差分を計算し、

`ADJUSTMENT_OUT / quantity = 2`

の履歴を作成する。

逆に、

システム上の在庫：10  
実在庫：12

の場合は、

`ADJUSTMENT_IN / quantity = 2`

とする。

現在庫と実在庫が同じ場合は在庫変動を発生させない。

---

# 13. 倉庫間移動

複数倉庫間で商品を移動できる。

1回の移動申請で複数商品を指定できる。

移動元倉庫と移動先倉庫は、同じ倉庫を指定できない。

倉庫間移動は以下のデータで管理する。

`stock_transfers`

倉庫間移動そのものを表す。

`stock_transfer_items`

移動対象となる商品と数量を表す。

同一の `stock_transfer` 内で同一商品を重複して持てないよう、`stock_transfer_id + product_id` にユニーク制約を設ける。

`stock_movements`

移動完了時に発生した実際の在庫変動を記録する。

倉庫間移動による履歴（TRANSFER_IN / TRANSFER_OUT）は、対応する `stock_transfer_items` の1行に紐づける。履歴の商品は、紐づく移動明細の商品と一致していなければならない。

1つの移動明細につき、TRANSFER_OUT と TRANSFER_IN の履歴は各1件のみ作成される。

## 13.1 stock_transfers が持つ記録項目

以下を保持し、誰がいつ操作したかを追跡できるようにする。

- 申請者（requested_by）
- 申請日時（`created_at` を申請日時として扱う）
- 完了者（completed_by、NULL許可）
- 完了日時（completed_at、NULL許可）
- キャンセル実行者（cancelled_by、NULL許可）
- キャンセル日時（cancelled_at、NULL許可）

completed の場合のみ完了者・完了日時を持ち、cancelled の場合のみキャンセル実行者・キャンセル日時を持つ。

---

# 14. 倉庫間移動ステータス

倉庫間移動は以下の3状態を持つ。

- pending
- completed
- cancelled

状態遷移は以下のみ許可する。

`pending → completed`

`pending → cancelled`

`completed` および `cancelled` は終端状態とする。

以下の遷移は禁止する。

- completed → pending
- completed → cancelled
- cancelled → pending
- cancelled → completed

---

# 15. 倉庫間移動申請

staff、manager、adminが申請できる。

申請時点では在庫を変更しない。

複数商品を1回の申請に含めることができる。

申請時、対象の商品および移動元・移動先倉庫は有効である必要がある。

---

# 16. 倉庫間移動完了

managerおよびadminのみ実行できる。

`pending` 状態のみ完了できる。

申請後に、対象の商品、移動元倉庫、移動先倉庫のいずれかが無効化されている場合は、完了できない（キャンセルのみ可能）。

完了処理時に、すべての商品について移動元倉庫の在庫を確認する。

1商品でも在庫不足の場合、移動全体を失敗とする。

すべての在庫が足りている場合のみ、

1. 移動元倉庫の在庫を減少
2. 移動先倉庫の在庫を増加（移動先に在庫レコードが存在しない場合は作成する）
3. 移動明細ごとにTRANSFER_OUT履歴を作成（移動元倉庫の変動として記録）
4. 移動明細ごとにTRANSFER_IN履歴を作成（移動先倉庫の変動として記録）
5. stock_transferをcompletedへ変更（完了者・完了日時を記録）

する。

これらは同一トランザクション内で実行する。

途中で失敗した場合はすべてRollbackする。

---

# 17. 倉庫間移動キャンセル

managerおよびadminのみ実行できる。

`pending` 状態のみキャンセル可能とする。

申請後に商品や倉庫が無効化されている場合でも、キャンセルは可能とする。

申請段階では在庫を変更していないため、キャンセル時の在庫戻し処理は発生しない。

キャンセル時は、キャンセル実行者・キャンセル日時を記録する。

---

# 18. ユーザー管理

ユーザーは以下の情報を持つ。

- 名前
- メールアドレス
- パスワード
- 権限
- 有効 / 無効

権限は以下の3種類とする。

- staff
- manager
- admin

ユーザーの新規登録・編集・無効化はadminのみ実行できる。

一般ユーザー向けの新規会員登録機能は作成しない。

すべてのユーザーはすべての倉庫の在庫状況を閲覧できる。

ユーザーを特定倉庫へ所属させる仕組みは設けない。

## 18.1 ユーザー管理の制約

- 最後の有効なadminは、無効化できない。
- 最後の有効なadminは、staff / managerへ降格できない。
- 自分自身の無効化はできない。
- 自分自身の権限（role）の変更はできない（変更が必要な場合は、別のadminが行う）。

複数のadminが同時に互いを無効化・降格しようとした場合でも、有効なadminが0人にならないものとする。

# 26. アーキテクチャ

基本構成は以下とする。

`Controller → UseCase / Service → Repository → Model → DB`

ControllerはHTTPリクエスト・レスポンスを担当する。

UseCaseは各業務処理の実行手順、業務ルール、トランザクション境界を担当する。

Repositoryはデータ取得・登録・更新を担当する。

ModelはEloquent Modelとしてテーブルとの対応、Relation、Cast等を担当する。

Serviceは必須レイヤーとはせず、複数UseCaseから共有される業務ロジックが発生した場合に使用する。

読み取りだけの単純な検索（一覧・検索・詳細表示）は、ControllerからRepositoryを直接呼んでよい。複数のRepositoryからの集約、閲覧条件の組み立て、結果の加工、業務上の表示ルールがある場合は、UseCaseまたは読み取り専用のQueryクラスを用いる。

権限の判定（誰が実行できるか）はGate / Policyが担当し、UseCaseは業務ルール（状態に依存する判定）と処理手順を担当する。

- Validation

- 在庫不足

- 小数・数値以外
- 境界値
- 同一処理内での同一商品の重複指定

- 状態遷移
- 不正な状態遷移
- pending中に商品・倉庫が無効化された移動の完了不可・キャンセル可
- 複数商品の一括処理
- Transaction
- Rollback
- 二重実行
- 同時実行時の在庫整合性
- 在庫と在庫履歴の整合性
- admin / manager / staffによる権限制御
- 削除可能条件（0在庫レコードの同時削除を含む）
- 削除不可条件

- 複数adminが同時に互いを無効化・降格した場合の、有効なadmin数の維持
- 自分自身の無効化不可

- 同じ商品×倉庫への初回入庫を同時に実行した場合の整合性
- 倉庫間移動の履歴と移動明細の商品の一致
- 1つの移動明細に対するTRANSFER_OUT / TRANSFER_INの重複作成不可（完了処理の二重実行）
- TRANSFER_OUTが移動元倉庫、TRANSFER_INが移動先倉庫の変動として記録されること

Feature Test、Unit Test、Repository Testを用途に応じて使い分ける。

特にUseCaseでは業務ロジックを重点的にUnit Testし、Repositoryをモック可能な構成とする。

実DBとの整合性についてはRepository TestおよびFeature Testで確認する。

トランザクション、ロック、Rollbackの動作は、実DBを使うFeature TestおよびRepository Testで確認する。UseCaseのUnit Testでは、Laravelの `DB` ファサードをモックせず、業務判断（例外の種類、判定の順序、Repositoryに渡す値）を確認する。
