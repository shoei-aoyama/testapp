# テストデータガイド（Factory / Seeder）

Factoryで作ったデータが「何を保証して、何を保証しないか」の一覧。テストを書くときは、まずここを確認する。

## 基本方針

- **Factoryは「単体でDB制約を満たすレコード」を作る。** 業務的に完全な状態（履歴・在庫・明細まで整合した状態）は作らない。
- 業務的に整合したデータが必要なときは、Seederやテスト用Helper（テスト設計の段階で作成）で、複数テーブルをセットで作る。
- Factoryの状態（state）は、DBのCHECK制約に反しない組み合わせだけを登録する。

## Factoryが保証すること / しないこと

| Factory                  | 保証すること                                                                                 | 保証しないこと                                                                                               | 状態（state）                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| UserFactory              | 有効な staff ユーザー                                                                        | —                                                                                                            | `admin()` `manager()` `staff()` `inactive()` `unverified()`                         |
| CategoryFactory          | 有効なカテゴリ（名前は重複しない）                                                           | —                                                                                                            | `inactive()`                                                                        |
| ProductFactory           | 有効な商品（コードは重複しない）。カテゴリ未指定なら新規作成。単価は約2割NULL                | 在庫・履歴                                                                                                   | `inactive()`                                                                        |
| WarehouseFactory         | 有効な倉庫（コードは重複しない）。郵便番号・住所・電話番号は値あり                           | 在庫・履歴。NULLのケース（明示的に指定する）                                                                 | `inactive()`                                                                        |
| InventoryFactory         | 在庫行1件（商品・倉庫未指定なら新規作成）                                                    | **履歴との整合**（履歴は作らない）                                                                           | —                                                                                   |
| StockTransferFactory     | 倉庫間移動の**ヘッダ**のみ。移動元≠移動先。ステータスと実行者・日時の組み合わせがCHECKに合う | 明細・履歴・在庫の増減。**`completed()` はヘッダを完了状態にするだけで、業務的に完全な完了済み移動ではない** | `pending()`（既定）`completed()` `cancelled()`                                      |
| StockTransferItemFactory | 移動明細1件（数量1以上）                                                                     | 履歴                                                                                                         | —                                                                                   |
| StockMovementFactory     | 履歴1件。既定は IN、数量1以上、移動明細なし。変更前後の数量が種別・数量に合う                | **現在庫（inventories）の更新**・履歴と在庫の整合                                                            | `out()` `adjustmentIn()` `adjustmentOut()` `transferIn(?item)` `transferOut(?item)` |

### StockMovementFactory の補足

- 数量まわり（`quantity` / `quantity_before` / `quantity_after`）を上書きするときは、3つをセットで指定する。食い違うとCHECK制約でエラーになる（意図した動作）。
- `transferIn()` / `transferOut()` は、明細を渡さない場合に「completed のヘッダに属する明細」を履歴1件ごとに作る。商品は明細の商品、倉庫は OUT なら移動元・IN なら移動先になる。数量は明細の数量とは連動しない。
- 1つの明細に対する TRANSFER_OUT / TRANSFER_IN は各1件まで（DBのユニーク制約）。同じ明細に両方作るときは、同じ明細を両方に渡す。

```php
// 例: 1つの明細に対する OUT と IN
$item = StockTransferItem::factory()
    ->for(StockTransfer::factory()->completed(), 'stockTransfer')
    ->create();

StockMovement::factory()->transferOut($item)->create();
StockMovement::factory()->transferIn($item)->create();
```

## Seeder

| Seeder          | 種類     | 内容                                                                             |
| --------------- | -------- | -------------------------------------------------------------------------------- |
| CategorySeeder  | 固定     | 商品 / 資材 / 備品                                                               |
| WarehouseSeeder | 固定     | 福岡・東京・大阪（有効）、旧名古屋（無効）。大阪は郵便番号・住所・電話番号がNULL |
| UserSeeder      | 固定     | admin / manager / staff / 無効ユーザー（下記）                                   |
| ProductSeeder   | 固定     | 10件。P-009 は単価NULL、P-010 は無効商品                                         |
| DummyDataSeeder | ランダム | 商品+40（うち4件は無効）、在庫、履歴、倉庫間移動13件                             |
| DatabaseSeeder  | —        | 上記を順に実行                                                                   |

### 固定アカウント（パスワードはすべて `password`、開発用）

| メール               | 権限    | 状態 |
| -------------------- | ------- | ---- |
| admin@example.com    | admin   | 有効 |
| manager@example.com  | manager | 有効 |
| staff@example.com    | staff   | 有効 |
| disabled@example.com | staff   | 無効 |

### DummyDataSeeder が保証すること

- 固定商品とダミー商品のうち、商品×有効倉庫の約7割に在庫を持たせる。
- 商品×倉庫ごとの履歴は、最初が入庫で、その後は入庫・出庫・棚卸調整を日時順に積み上げる。変更前→変更後の数量がつながり、最後の数量が `inventories.quantity` と一致する。
- 在庫が0未満になる出庫は作らない。
- 完了済みの倉庫間移動（5件）は、通常の履歴がすべて終わったあとのイベントとして、日時順に追加する。明細・TRANSFER_OUT・TRANSFER_IN・在庫の増減がセットで作られる。
- pending（5件）・cancelled（3件）は、ヘッダと明細だけで、在庫・履歴は動かさない。
- 履歴の日時は、通常履歴が90日前〜10日前、完了済み移動が9日前〜1日前。履歴のidの順序は日時の順序と一致する。

### 実行方法

```bash
# 固定 + ダミーをまとめて（テーブルを作り直す）
php artisan migrate:fresh --seed

# 固定データだけ
php artisan db:seed --class=CategorySeeder
php artisan db:seed --class=WarehouseSeeder
php artisan db:seed --class=UserSeeder
php artisan db:seed --class=ProductSeeder
```

DummyDataSeeder は、固定データを先に入れておく必要がある（なければエラーで止まる）。
